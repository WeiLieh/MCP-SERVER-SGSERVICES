## MCP Failure Transparency
- [2026-10-12] No fallbacks: `api/bus.js` no longer switches to the data.gov.sg (NEA) APIs, Open-Meteo, or the hard-coded ASEAN dataset when an MCP call fails. Every section comes only from `vdineshk/sg-weather-data-mcp`; a failed call is reported, never replaced.
- [2026-10-12] Nothing hard-coded: removed the hard-coded ASEAN climate table, the front-end placeholder values (`28°C`, `Partly Cloudy`, `25° / 34°`, `81%`, `6 km/h`), the fixed `1.2897°, 103.8501°` location line, the hard-coded postal code/sector tables and the `238823` default location, the fixed `HTTP 200` / `Reachable` defaults, the hard-coded Authorization Server line, and the hard-coded MCP tool list (now read live from the MCP `tools/list`).
- [2026-10-12] Current temperature and humidity come only from the MCP `get_sg_forecast` (24h) response. If the MCP server returns a current reading it is shown; otherwise the MCP 24-hour range is shown (e.g. `25–33°C`, `60–95%`). Nothing is calculated or invented.
- [2026-10-12] Shared MCP client `api/_mcp.js` (underscore prefix = not deployed as a Vercel function, so there are still exactly 2 serverless functions). It performs the MCP `initialize` handshake (with `Mcp-Session-Id`), checks `response.ok` before reading any body, detects JSON-RPC errors and tool `isError` results, times out after 15s (changed to 10s on 2026-10-12, see below), and redacts the key from every reason string.
- [2026-10-12] `/api/bus` response format: one entry per section (`get_sg_psi`, `get_sg_weather_now`, `get_sg_forecast_24h`, `get_sg_forecast_4day`, `get_asean_climate`), each `{ ok, status, data }` or `{ ok: false, status, reason }`, plus `ok` and a `failures` list. When any MCP call fails, the HTTP status is the first failure's upstream status (non-2xx), and the body still carries the sections that succeeded.
- [2026-10-12] `/api/health` performs `initialize` + `tools/list` and returns `answered`, `ok`, `status`, `latencyMs`, `keyConfigured`, `server`, `tools`, and a one-line `reason`.
- [2026-10-12] Front end when MCP fails: a red banner at the top of both tabs lists every failing MCP call (`tool · HTTP status · reason`), including `/api/health`. Each failed section (PSI, Weather forecast, 4-Day Forecast, Weather now — shown even while the accordion is collapsed, ASEAN) is replaced by an `MCP call <tool> failed` card with the HTTP status and reason. The `Smithery MCP Service` card shows `Checking…`, `Reachable`, `Error` or `Unreachable` from the real health result, and the HTTP / Auth card shows `Authenticated`, `Unauthorized` or `Failed`.
- [2026-10-12] A missing PSI reading shows a grey `No data` card instead of defaulting to `Good`.
- [2026-10-12] Postal code / geolocation: lookup failures are shown as a message instead of substituting a hard-coded address. PSI region mapping uses MCP `region_metadata` coordinates when present, otherwise the 5 NEA region centroids (`REGION_COORDS`), which remain the only fixed geographic constants.
- [2026-10-12] MCP rate limit (HTTP 429) handling: `/api/bus` calls the MCP tools one at a time (not in parallel). An HTTP 429 reply is retried up to 2 times, waiting for the server's `Retry-After` (capped at 3s) or 1s/2s backoff. Per-request timeout is 10s and `/api/bus` may run up to 60s on Vercel (`maxDuration`).
- [2026-10-12] MCP result reuse: successful MCP results are reused for up to 5 minutes (in-memory per server instance, plus Vercel CDN `s-maxage=300` on fully successful responses) so each page view doesn't trigger a new burst of MCP calls. Only real MCP data is reused, never past its 5-minute window; failed calls are never cached (`Cache-Control: no-store`) and are always shown on screen.
- [2026-10-12] The front end runs the `/api/health` check after `/api/bus` finishes, not at the same time.

## MCP Error Diagnostics
- [2026-10-13] When the MCP server replies with a non-2xx status, the failure reason now names the step that failed (`initialize`, `tools/list`, or `tools/call <tool>`), lists the server's rate-limit / retry headers (any header containing rate, retry, limit, quota or reset), and quotes the first 200 characters of the reply body. The key is redacted from all of it. This shows in the red banner, on each failed section, and in `/api/bus` and `/api/health` JSON. Purpose: find the root cause of the ongoing HTTP 429 (per-minute burst limit vs a daily/plan quota) before choosing a fix.
- [2026-10-13] Single tool check without opening the app: `/api/bus?tool=get_sg_psi` (or any of the 4 tools) runs just that one MCP call and returns its JSON or the failure reason.
- [2026-10-13] Option B (longer per-tool caching) is on hold until the 429 root cause is known.
- [2026-10-13] Root cause of the HTTP 429: the MCP server `vdineshk/sg-weather-data-mcp` is on a free tier limited to 5 tool calls per day ("Rate limit exceeded. Free tier: 5 calls/day.", `calls_remaining_today: 0`). Listing tools (`/api/health`) does not count against it. The app needs 5 tool calls per full load, so the free tier supports at most one full load per day. Caching (option B) alone cannot fix this.
- [2026-10-13] Short on-screen reasons, full details in JSON (supersedes the 2026-10-13 diagnostics entry above): every MCP failure now has a short one-line `reason` (max 200 characters) built from the MCP server's own message, e.g. `HTTP 429 on tools/call get_asean_climate: Rate limit exceeded. Free tier: 5 calls/day. (0 calls left today) [after 2 retries]`. This short reason is what the red banner and the section error cards show.
- [2026-10-13] Full MCP error in both endpoints' JSON: each failure also carries an `upstream` object with `stage` (`initialize`, `tools/list` or `tools/call <tool>`), `status`, `headers` (rate-limit / retry headers) and `body` (the MCP server's complete reply, parsed as JSON when possible, never cut off, key redacted). It appears in `/api/bus` under each failed section (e.g. `get_sg_psi.upstream`), in `/api/bus?tool=<tool>`, and in `/api/health` when the health check fails. Built once in the shared helper `api/_mcp.js`.
- [2026-10-13] `/api/health` labels what it checked: on success it returns `checked: "server reachable, key accepted (tool quota not checked)"` and the reason `MCP server answered: server reachable, key accepted (tool quota not checked)`, shown on the `Smithery MCP Service` card. A 200 from `/api/health` does not mean tool calls will succeed, because health never runs a tool and the 5 calls/day quota only counts tool calls.
- [2026-10-13] Retrying a 429 is unchanged (still up to 2 retries), even for the daily quota; stopping retries on a daily-quota 429 was proposed but not requested.
- [2026-10-13] Vercel environment variables are set per environment (Production / Preview / Development). `SMITHERY_API_KEY` is set for Production only, so preview deployments of PRs fail with `HTTP 401 on initialize: invalid_token` and `/api/health` shows `keyConfigured: false`. This is expected for now: previews are useful for checking layout and error messages, not live MCP data. Adding the key to Preview would make previews work, but they would share the 5 tool calls/day quota with production.
